# K8S-使用笔记

## 常用K8S版本

| 特性维度 | k3d | kind | minikube | k3s | k0s | MicroK8s |
| --- | --- | --- | --- | --- | --- | --- |
| 本质与定位 | k3s 的 Docker 封装器，在 Docker 中运行 k3s | 标准 K8s 在 Docker 中运行的测试工具 | 本地开发专用的单节点集群工具 | 轻量级 K8s 发行版，CNCF 认证 | 零摩擦的单二进制 K8s 发行版 | Ubuntu 生态的轻量级发行版 |
| 底层实现 | Docker 容器作为节点，运行 k3s | Docker 容器作为节点，运行标准 K8s 组件 | 通常在 VM 中运行单节点集群；也支持 Docker 模式 | 单一二进制文件，所有组件打包为一个进程 | 单一二进制文件，包含所有 K8s 组件 | Snap 包形式安装，支持多节点 |
| 资源消耗 | 极低 (继承自 k3s) | 中等 | 较高 (VM 模式) / 中等 (Docker 模式) | 极低 (二进制约 50-100MB，内存约 512MB) | 极低 (最低 1 核 CPU/1GB 内存) | 低 |
| 启动速度 | 极快 (秒级) | 快 (秒级) | 较慢 (VM 启动耗时) | 极快 (约 30 秒) | 极快 (单文件启动) | 快 |
| 多节点支持 | 核心特性，一条命令创建多节点 | 核心特性，配置简单 | 支持但配置相对繁琐 | 需手动配置或额外工具 | 核心特性，支持高可用多控制平面 | 支持 |
| K8s 版本 | 裁剪版 K8s (跟随 k3s 版本) | 标准 K8s (跟随社区版本) | 标准 K8s | 裁剪版 K8s (通常滞后社区 1-2 个小版本) | 标准 K8s | 标准 K8s |
| 内置组件 | 内置 Traefik Ingress (继承自 k3s) | 无 Ingress Controller，需自行安装 | 丰富的 Addons (Ingress, Dashboard 等) | 内置 Traefik Ingress、CoreDNS、本地存储等 | 内置 CoreDNS、Metrics Server 等 | 内置 DNS、Dashboard、Storage 等 |
| 架构支持 | 支持 ARM64, ARMv7 (继承自 k3s) | 主要 AMD64 | 主要 AMD64 | 支持 ARM64, ARMv7 (IoT / 边缘友好) | 支持 x86_64, ARM64, ARMv7, RISC-V | 主要 AMD64 |
| 生产可用性 | 否 (设计目标为开发 / 测试) | 否 (设计目标为测试) | 否 (设计目标为本地开发) | 是 (CNCF 认证，可用于生产) | 是 (支持高可用部署) | 是 (可用于生产) |

## 配置管理工具

两者都是 K8S 应用部署与配置管理工具，核心区别在于思路不同：

- **Helm**：K8S 的包管理器。将应用打包为 Chart（模板 + 默认值），通过 `helm install` 一键部署，支持版本管理、回滚和仓库分发，适合需要复用和分发的通用应用。
- **Kustomize**：原生的配置叠加工具（`kubectl apply -k`）。不引入模板语法，而是通过 Overlay 机制对基础 YAML 做 patch，适合追求纯 YAML、不想引入额外工具链的场景。

> 简单选择：需要模板化和版本管理 → Helm；需要轻量、纯 YAML 的环境差异管理 → Kustomize。
