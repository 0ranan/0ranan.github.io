# 一次 host key 变更引发的隧道失联

早上开终端连跳板机，先看到的是这个：

```
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
Offending ECDSA key in /home/anran/.ssh/known_hosts:3
Host key for liuzhanghao.xinmiao.net.cn has changed and you have requested strict checking.
Host key verification failed.
```

这台跳板（阿里云 `iZbzqxbxvh30klZ`，`47.100.19.156`，admin 用户）在 11-11 00:30 重装过系统。重装会重新生成 `/etc/ssh/ssh_host_*`，host key 变了本身是预期行为。

先确认新指纹对不对得上：

```bash
$ ssh-keyscan -T 5 -t ed25519 liuzhanghao.xinmiao.net.cn | ssh-keygen -lf -
256 SHA256:hmRBSZ4DKyu1kLhgsGZH4huIeYuueapgktwmUfLzX2M liuzhanghao.xinmiao.net.cn (ED25519)
```

和报错里给的一致。known_hosts 是哈希存储的，`:3` 对应的明文主机名看不到，清记录得用 `ssh-keygen -R`：

```bash
$ cd ~/.ssh
$ cp known_hosts known_hosts.bak.$(date +%Y%m%d-%H%M%S)
$ for h in liuzhanghao.xinmiao.net.cn 47.100.19.156 '[47.100.19.156]:4021'; do
    ssh-keygen -f known_hosts -R "$h"
  done
```

清完再连，报的是 `Permission denied (publickey)`，host key 这一关过了，卡在认证上。重装后 `authorized_keys` 也是新的，这是第二件事。

## 真正要命的不是跳板

这台跳板还挂着一条反向隧道。`oe-jj0` 是内网一台 openEuler 22.03（aarch64），它主动连出去，把自己的 22 口挂在跳板的 4021 上：

```
[本机] --TCP--> 47.100.19.156:4021 (跳板 sshd 监听)
                        ^
                        |  oe-jj0 执行 -R 0.0.0.0:4021:127.0.0.1:22
                  oe-jj0:22
```

平时 `ssh oe-jj0` 走的就是 4021。跳板重装后 4021 没了，`nc -vz 47.100.19.156 4021` 直接 `Connection refused`。

从 nas-debian 跳到跳板查日志，`112.27.230.199` 每隔 10 秒来连一次：

```
Nov 11 10:06:33 iZbzqxbxvh30klZ sshd[18117]: Connection closed by 112.27.230.199 port 6096 [preauth]
Nov 11 10:06:43 iZbzqxbxvh30klZ sshd[18121]: Connection closed by 112.27.230.199 port 6097 [preauth]
Nov 11 10:06:54 iZbzqxbxvh30klZ sshd[18123]: Connection closed by 112.27.230.199 port 6098 [preauth]
```

从开机到当时一共 3877 次，间隔正好 10 秒，是 systemd `RestartSec=10` 在重启 `reverse-ssh.service`。跳板上抓包看客户端 banner：

```
SSH-2.0-OpenSSH_8.8
```

openEuler 22.03 自带的 OpenSSH。它连上来做 KEX，拿到跳板的新 host key，和 known_hosts 里的旧 key 一比，不匹配就关连接。日志里没有 `authenticating user admin`，说明认证根本没开始。

死锁就是这样成型的：进 jj0 要走 4021，4021 要靠 jj0 的隧道，隧道客户端卡在 host key 校验。跳板修得越干净，jj0 越进不来。

```bash
$ sudo journalctl -u ssh --no-pager -b | grep "Accepted publickey" | grep -oE 'from [0-9.]+' | sort | uniq -c | sort -rn
```

成功的登录就三类来源：`100.104.x.x` 是阿里云 Workbench（控制台 VNC 走的内网地址），`117.89.43.14` 是另一个公网出口，`117.86.10.46` 是 nas-debian 的出口。没有陌生地址。

失败的条数就比较扎眼了：

```bash
$ sudo journalctl -u ssh --no-pager -b | grep -ciE "Failed|Invalid user|Connection closed by"

```

这个数不能直接当爆破量，其中 3988 条是 jj0 每 10 秒的重试。拆开看：

```bash
$ sudo journalctl -u ssh --no-pager -b | grep -c 'Invalid user'
487
$ sudo journalctl -u ssh --no-pager -b | grep -c 'Failed password'
0
```

`Invalid user` 487 条，`Failed password` 是 0。密码认证早就关了，扫描器连试密码的机会都没有。抽几条出来：

```

Nov 11 09:55:48 iZbzqxbxvh30klZ sshd[16907]: Invalid user admin1 from 118.145.239.129 port 35264
```

`45.148.10.x` 这一段反复出现，`root`、`admin`、`admin1`、`ubuntu` 轮着试，是字典扫描。一晚上 487 次，量不算大，但 22 直接开在公网，被真爆破只是时间问题。

当前有没有人在线上：

```bash
$ sudo ss -tnp | grep ':22'
ESTAB 0 404 [::ffff:172.24.56.205]:22 [::ffff:117.86.10.46]:53910
```

只有我自己这一条。结论是没被登进去：成功登录全部来自已知地址，`authorized_keys` 里 7 把 key 的注释也都认识（`swas-imported-key`、`anran@nas-debian-13`、`hoperun-domain\liu_zhanghao@note220221` 这些）。sshd 现状：

```bash
$ sudo sshd -T | grep -Ei '^port|^passwordauthentication|^permitrootlogin'
port 22
passwordauthentication no
permitrootlogin yes
```

`permitrootlogin yes` 但密码关着，只能拿 key 进。等 4021 恢复，在安全组里把 22 的来源收窄，或者干脆只留 4021。

## 试过的一个取巧办法，没用

known_hosts 按 key 类型分别记录。jj0 大概率只缓存过 ed25519，而隧道 unit 里写的是 `StrictHostKeyChecking=accept-new`，它只对“没见过的主机”生效。那就让跳板只提供 RSA：

```bash
$ printf 'HostKeyAlgorithms rsa-sha2-512,rsa-sha2-256\n' | sudo tee /etc/ssh/sshd_config.d/99-tmp-rsa-only.conf
$ sudo sshd -t && sudo systemctl reload ssh
$ sudo setsid bash -c 'sleep 300; rm -f /etc/ssh/sshd_config.d/99-tmp-rsa-only.conf; systemctl reload ssh' &
```

想法是 RSA 对 jj0 算“未知主机”，`accept-new` 会自动接受，隧道就能起来。等了两分钟，4021 还是 refused；改成只提供 ECDSA 再试，一样。jj0 的 known_hosts 里三种旧记录应该都在，也可能是它实际跑的是 `StrictHostKeyChecking=yes`，不是文档里写的 `accept-new`。对客户端来说，“key 变了”和“主机不存在”是两回事，换类型绕不过去。

改完立刻把配置删了，`sshd -T` 回到默认的 ed25519 打头：

```bash
$ sudo rm -f /etc/ssh/sshd_config.d/99-tmp-rsa-only.conf /etc/ssh/sshd_config.d/99-tmp-ecdsa-only.conf
$ sudo sshd -t && sudo systemctl reload ssh
$ sudo sshd -T | grep -i '^hostkeyalgorithms' | cut -c1-60
hostkeyalgorithms ssh-ed25519-cert-v01@openssh.com,ecdsa-sha
```

## 现在的状态

跳板 22 是通的，本机的 key 登不上，重装后 authorized_keys 只剩 7 把别的 key。jj0 仍然每 10 秒重试，端口号从 6096 一路涨到 6127 还在涨。

`112.27.230.199:22` 看着像 jj0，其实是它出口 NAT 后面另一台设备：banner 是 `SSH-2.0--`，只给 RSA key，扫端口也只有 22。不是 jj0 的 sshd，从这里进不去。

本机 `192.168.3.0/24` 和 nas `192.168.1.0/24` 都扫过 22 端口，没有 jj0。

## 还能走的两个方向

**一、从阿里云快照取回旧 host key。** 这是唯一不用碰 jj0 的路：

1. 控制台找 11-11 00:30 之前的系统盘快照
2. 用快照建一块云盘，挂到临时实例，取 `/etc/ssh/ssh_host_{ed25519,rsa,ecdsa}_key*`
3. 覆盖回跳板的 `/etc/ssh/`，权限 `root:root 600`，`systemctl reload ssh`
4. `ss -lntp | grep 4021` 出现监听，jj0 会在 10 秒内自己连上

key 放回去之后，本机和 nas 现在记的是新 key，会反过来报 host key 变了，两边都得重新 `ssh-keygen -R` 再接受。

**二、找一个新入口。** 办公网任意一台机器能 ssh 到 jj0 就行，进去执行：

```bash
ssh-keygen -f /root/.ssh/known_hosts -R 47.100.19.156
systemctl restart reverse-ssh
```

重启 jj0 没用，known_hosts 在磁盘上，重启后还是同一个错误。

## 备份清单

跳板机重装前：

```bash
sudo tar czf /root/ssh-hostkeys-$(date +%F).tgz /etc/ssh/ssh_host_*
```

重装后放回去，所有依赖它的客户端都不用动。

jj0 上的 unit 建议单独用一份 known_hosts，别和日常登录混在一起：

```ini
ExecStart=/usr/bin/ssh -N -T \
  -o UserKnownHostsFile=/root/.ssh/known_hosts.jump \
  -o StrictHostKeyChecking=accept-new \
  -o ServerAliveInterval=15 -o ServerAliveCountMax=3 \
  -o ExitOnForwardFailure=yes -o BatchMode=yes \
  -i /root/.ssh/id_rsa \
  -R 0.0.0.0:4021:127.0.0.1:22 admin@47.100.19.156
Restart=always
RestartSec=10
```

`known_hosts.jump` 用 `ssh-keyscan -t ed25519 47.100.19.156 > /root/.ssh/known_hosts.jump` 预置。以后跳板换 key，删这个文件重建就行，不波及别的连接。

`StrictHostKeyChecking=accept-new` 只能兜住第一次，兜不住换了 key。这次卡住，就是把它当成万能兜底了。
